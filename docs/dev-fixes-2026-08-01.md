# Dev fix list — from the 2026-08-01 trial run
*Self-contained: every item states the symptom, the evidence (with exact values you can reproduce), and the required behavior. Plan references are to yuna_plan.md stamped 2026-08-01 16:05 UTC — eight laws changed today; items 11–16 implement them. Priority order.*

## CRITICAL

**1 · Book valuation uses a stale price for AVGO — NAV is wrong by ~2.4%.**
Symptom: the positions/NAV valuation prices **AVGO.US 39 sh at ~$300.41**, but the `prices` table's latest bar (2026-07-31) closes at **$389.28** — verified identical against the vendor's live quote. Six of seven holdings reconcile against their latest bars to the penny (ANET 180.35 · NVDA 174.75 · TSM 245.22 · ISRG 353.33 · CNQ.TO 66.78 · VRT); only AVGO doesn't. So the `prices` ingest is fine — **the valuation join is grabbing a stale/cached bar for one ticker** (check: join keyed on a snapshot date, a per-ticker cache, or a `d` filter that AVGO alone misses). Required: at every NAV build, each holding is valued at its latest `prices` bar — no snapshots, no caches. Recompute/patch affected `nav` history. Correct book equity is ~C$73,627 and NAV ~C$205,813 as of 07-31 close (was showing 68,768 / 200,954).

**2 · New hard canary in `nightly-ingest` (plan §4.2, new law).**
After revaluation, assert per holding: `valuation_price == latest prices.close` (tolerance $0.005). Any mismatch → the run **FAILS** (red, not amber), naming the ticker and both prices in the run log. This is what would have caught item 1 automatically.

**3 · `nav` table has duplicate rows for 2026-07-31.**
Two rows for the same date were observed (NAV marked "provisional" in briefs because of it). Dedupe, and add a uniqueness constraint on the date key (or date+account if that's the grain) so upserts can't double-write.

## HIGH

**4 · Engine provenance must flow into memos and tickets automatically.**
`fundamentals.engine_agrees = false` means the final engine is **growth-derived** (= `min(revenue_cagr_3y, 25%)`), and plan §3.1 requires the words "growth-derived" on the bench row **and every memo/ticket that cites the engine**. Current top bench: MEDP, VEEV, NOW, ANET are all `engine_agrees=false`; only ADSK is `true`. Required: memo/ticket templates read provenance from the flag — never free-text. Template string when false: *"engine growth-derived (observed 3-yr revenue growth, capped) — measured engine failed the ±5pp cross-check; §3.3 guardrails apply."*

**5 · CNQ.TO has a null MCN — violates always-scored.**
Every holding carries an MCN every run (plan law). CNQ.TO's is null — likely the momentum scorer skips TSX tickers or a data gap goes unhandled. Required: score it; if inputs are genuinely missing, the row must say why (named gap), never null silently.

**6 · NUE.US got two different MCNs in the same run: 77.0 (candidates) vs 63.9 (queue).**
One name, one score, one run. Find the double-compute — most likely the candidate scorer and the queue writer use different as-of dates or ranking windows (all ranking windows end 10 trading days back, per §3.2). Single source of truth: queue rows copy the candidate score, never recompute.

**7 · Compounder queue rows are stale and use an unlegislated state.**
ZM / VEON / HRMY rows reference a superseded bench, and their state reads **"WATCH"** — not a state that exists in the plan. Purge rows on bench rebuild; constrain `state` to the legislated enum.

**8 · `nightly-ingest` ran at 05:23 UTC against a 02:00 UTC spec.**
The retry job (03:00) and the R2→R1 ordering assume the spec time. Fix the schedule (GitHub cron drift/queueing — consider an earlier cron with a gate, or self-check), and have the heartbeat row record scheduled-vs-actual; drift > 30 min → amber flag in the run log.

**9 · Earnings table needs `last_reported` (it's forward-only and that's ambiguous).**
Observed: MEDP.US has **no row at all** in the forward window while VEEV (2026-08-26) and ADSK (2026-08-27) do — for a July reporter that almost certainly means "already reported, next is beyond the window," but the system can't distinguish that from a calendar gap. Required: store `last_reported_date` per ticker (vendor has it), so blackout logic and briefs can say which case it is. Also: `report_when` is null on VEEV's row — populate when the vendor provides it.

## MEDIUM — implements today's plan-law changes

**10 · Compounder entry orders (plan §3.1, new law).** Entry = **GTC buy limit at the hurdle price** (fills anywhere at/below the hurdle, waits above it). Cancel/replace the order when a filing recomputes the hurdle — never on quote moves. Ticket generator + order-state tracking accordingly.

**11 · Averaging-down bands now measure from the entry fill (plan §3.1, changed law).** Adds require price below hurdle **and** below the entry fill; 5–15% below the fill → 50% add, beyond 15% → 100%. Entry day arms nothing regardless of gap-to-hurdle. The adds engine therefore needs the **fill price** stored per position (confirm the book schema has it; add if not).

**12 · MCN < 70 never tickets (plan §3.2, new law).** BUY-state names below 70 stay queued — the arming pass must not emit entry tickets for them (observed: RS.US armed at MCN 63.9).

**13 · Ticket fields (plan §5.1, new law).** Every entry ticket names: **account · currency with FX estimate printed · theme · risk in C$ and % of NAV**. Risk is CAD-converted before the % (a USD-risk ÷ CAD-NAV slip produces ~0.16% where the truth is 0.24% — that exact error occurred). Effective-bets printed per ticket (existing law): each ticket carries its **own** post-fill number.

**14 · R1 snapshot restates the full blackout wall, holdings included (plan §5.1, new law).** Every brief, self-contained — observed failure mode: a Tuesday brief omitted a holding (CNQ.TO, reporting 8/6) because Monday's brief had listed it.

**15 · One position, one account, one order (plan §2.6, new law).** If the placement-priority account can't fund the full size (e.g., RRSP cash C$22,747.65 vs a C$24,698 full position), route to the next account that can fund it whole. Never split a position across accounts; never assume a top-up.

**16 · Whole-share sizing rule — ceil into the band.** Target weight is the §3.1 size (12% now); pick the share count whose weight lands **at or above** target while inside the band — i.e., ceil when flooring would land below 12.0%. Worked example at NAV C$205,813, FX 1.402: MEDP @577.11 → 30.52 → **31 sh** (12.19%) ✓; VEEV @203.78 → 86.45 → **87 sh** (12.08%) ✓. (Momentum sizing is risk-budget-based and floors instead — budget is a ceiling there.)
