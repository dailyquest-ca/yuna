# Incident — production database down, disk full (2026-08-03 01:49 UTC)

**Status: OPEN. The database cannot recover on its own; it needs a disk resize in the Supabase
dashboard. This cannot be fixed from SQL, from the API, or from this repo.**

## What happened

```
01:49:52  ERROR  cannot execute INSERT in a read-only transaction     <- backfill dies
01:49:53  ERROR  cannot execute UPDATE in a read-only transaction     <- so does report_fail
01:49:56  LOG    database system was not properly shut down; automatic recovery in progress
```

Postgres flipped read-only to protect itself. Then it got worse than read-only: crash recovery
replays the write-ahead log, and finishing that replay needs to WRITE. There was no room.

```
LOG    redo starts at 1/25000028
LOG    redo done at 1/5AFFFF20
FATAL  could not write to file "pg_wal/xlogtemp.NNNNNN": No space left on device
LOG    startup process exited with exit code 1
LOG    shutting down due to startup process failure
```

That loop has repeated every ~25 seconds since. The instance is not degraded — it is **down**, and
it cannot self-heal, because recovery is precisely the thing that needs the space it lacks. The
project API still reports `ACTIVE_HEALTHY`; that describes the control plane, not the database.

## The backfill was the trigger, not the cause

My first reading — "the ten-year backfill filled the disk" — does not survive arithmetic.

The organization is on **pro**, so the disk is 8 GB. The full ten-year `prices` table is nowhere
near that:

| | rows | heap | + PK index | total |
|---|---|---|---|---|
| before (3 yr) | 2.21M | ~220 MB | ~130 MB | ~350 MB |
| after (10 yr) | ~7.4M | ~750 MB | ~400 MB | ~1.2 GB |

And the backfill never got close to writing that. It ran for **about 2.5 minutes** (01:47:15 →
01:49:52) with 8 workers against a per-name endpoint. At that rate it had fetched a few hundred
names — on the order of 10⁵–10⁶ rows, perhaps 100–200 MB. **A disk with meaningful free space does
not fill in 2.5 minutes at that write rate.** It was already at the wall; the backfill was simply
the next writer to touch it.

### What actually consumed the 8 GB — leading hypothesis, unverified

I cannot confirm any of this while the database is down, so it is stated as a hypothesis with its
reasoning, to be checked the moment there is a connection.

1. **`fundamentals.raw_doc`.** §4.3 keeps the full EODHD filing document beside every extract, for
   2,834 names. A single US-equity fundamentals document — full statement history, holders,
   earnings history, ESG, insider transactions — is megabytes before compression. At even ~700 KB
   stored per row that is ~2 GB, and it is plausibly more.
2. **Dead-tuple bloat from the re-extraction I ran at 14:55 UTC on 2026-08-02.** It UPDATED 2,734
   of those rows. Postgres writes a whole new row version on update and leaves the old one until
   vacuum; on a large TOASTed table autovacuum lags badly. That run plausibly doubled the
   fundamentals footprint in a single pass, hours before the disk gave out.
3. **WAL.** Every write that day — the re-extraction, score, rank, ingest, migration 032's delete
   of 427 rows — generated WAL, and PITR retains it. `pg_wal` is literally the directory named in
   the fatal error.

The honest summary: I ran two large write operations against this database within twelve hours —
a full re-extraction in the morning and a bulk backfill at night — without ever looking at how much
disk either would consume, and the second one found the wall the first one had built.

## What this cost

- **Yuna is offline.** Every scheduled job and all five sessions are paused (below) rather than
  left to fail on a loop.
- **No expected data loss.** The failed transaction rolls back; `prices` upserts are idempotent, so
  a partial backfill leaves valid rows, not half-rows. **Verify, do not assume.**
- Supabase Pro holds daily physical backups, and `backup` commits a logical dump to the repo. Both
  are fallbacks if recovery ever fails outright.

## The fix (needs Zak — infrastructure and billing)

Supabase dashboard → project → **Settings → Compute and Disk → Disk size** → increase it. Growing
the volume lets the startup process finish its WAL write; recovery then completes and the instance
returns on its own. If the dashboard refuses while the database is down, Supabase support can
resize directly.

**Then, before restoring the schedule — in this order:**

1. **Find out what is actually using the disk.** This is the question the incident turns on:
   ```sql
   select relname, pg_size_pretty(pg_total_relation_size(c.oid)) as total,
          pg_size_pretty(pg_relation_size(c.oid))       as heap,
          n_dead_tup
     from pg_class c
     join pg_namespace n on n.oid = c.relnamespace
     left join pg_stat_user_tables s on s.relid = c.oid
    where n.nspname = 'public' and c.relkind = 'r'
    order by pg_total_relation_size(c.oid) desc limit 15;
   ```
2. **Reclaim.** `vacuum (full, analyze) fundamentals;` if bloat is the story — it rewrites the
   table and returns the dead space, and it needs free disk to do it, so it comes *after* the
   resize, never before.
3. `select count(*), min(d), max(d) from prices;` — how much of the backfill landed.
4. `select job, status from runs order by id desc limit 10;` — the `backfill` row is stuck at
   `running`; it died before it could mark itself red.
5. **Run `check` first.** It writes nothing but its own report row, which makes it the safest
   possible first contact with a database fresh out of recovery.
6. Only then restore the schedules (crons are commented out verbatim in `.github/workflows/*.yml`)
   and re-enable the five Routines.

## The question this raises for the plan

§4.3 says fundamentals are "kept forever … the raw filing JSON lives beside them as `jsonb` — one
queryable point-in-time asset". If that archive is most of an 8 GB disk at 2,834 names on its first
sweep, then the law as written has a capacity consequence nobody has priced: every subsequent sweep
rewrites those documents, and each rewrite costs a second copy until vacuum. That is a plan
question — retention, compression, or a separate store — and it needs an announced edit, not a
quiet trim.

## What I got wrong

I sized the backfill's **API** cost (~2,762 units against a 100,000/day limit — trivially
affordable) and never sized its **disk** cost. Tripling the largest table is a storage decision, not
a quota decision, and I checked the wrong budget. Worse, I had already run the morning's
re-extraction over every stored document without checking either.

The deeper failure is that neither job could see the resource it was consuming. A job that can fill
a disk should ask how much room is left before it starts, and stop while there is still enough left
to recover in. Nothing in this system asked.
