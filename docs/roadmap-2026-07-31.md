2,177,220 bars through 2026-07-31 · 2,754 fundamentals rows · 1,763 earnings rows · 150
candidates (13 BUY) · 17 queue · 67 bench (**0 approved**) · 7 open positions · 45 tickets (**all
`proposed`, ~3× duplicated across phase0 re-runs**) · 0 transactions · 8 briefs · every job green.

| Phase (§4.8) | Reality |
|---|---|
| A — repo, core schema, ingest, heartbeat | complete |
| B — M1–M3, MCN, queue states | complete, but built against the pre-simplification plan |
| C — schema, briefs, **scheduled sessions** | schema and `briefs` rows exist; **no session exists** |
| D — C1, CCN, hurdle, funnel, M4 | complete, with four unratified deviations |
| E — backtest | complete, both sleeves; **now measures rules the plan has since amended** |
| F — cutover, §6 Phase 0 | computed three times, **nothing executed**; book still `sleeve='unassigned'` |

**The one-line summary: the machine can compute and cannot yet operate.** Three facts make that
concrete, and all three are consequences of the same missing layer, not separate bugs:

1. **`select sleeve, count(stop) from book` returns zero stops on all seven positions.** §4.6 says
   protection lives at the broker; the machine holds no record of a single stop, so R2 cannot tell
   Zak whether his GTCs are right, and `daily.py:ratchet` filters on `sleeve='momentum'` — which
   no row is — so the trail engine is running over an empty set every night.
2. **No job has ever written a steady-state ticket.** `daily.py` detects fired stops, ±7% gaps and
   hurdle crossings and files them in a brief. §3.0 says each of those *is* a ticket, same day.
3. **Nothing reaches Zak.** Five sessions are specified in §4.4/§5; zero exist. A brief written to
   a table nobody reads is not a brief.

### 1B — Rules with no implementation at all

Grouped by what breaks if we go live without them. Every one verified absent by grep, not assumed.

**Cannot operate:** steady-state ticket generation (§3.0 event table, all eight rows) · market-gate
flip → sleeve to cash (`rank.py` records `flipped`; nothing acts) · live exits on trend-template
fail and MCN < 55 · the pyramid state machine (`book.pyramid_step` is never advanced, so the
breakeven ratchet that keys off full size can never fire) · the fill loop (`tickets.state` never
transitions; `transactions` has zero rows) · the five sessions · **the daily M3 re-scan** — §3.2
says WAIT names are re-scanned nightly and §3.0 puts the trigger check in the pre-open run, but
base detection lives only in the Saturday job.

**Unsafe:** quarantine (§4.1 — a bad tick can fire a real stop, two-source agreement is not
implemented) · corporate-action refresh (§4.1 — no splits/dividends feed; the first 4:1 split
reads as −75% and fires false alarms) · single-name 25% cap · displacement +10 · 2-new-entries-per-brief
throttle · 7–9 total position count · effective-bets computation (no correlation code anywhere) ·
crash protocol and tactical lots · averaging down · callable-facility never-increase-into-strength.

**Dishonest:** delisted-name retention (the survivorship bias in every backtest number we have) ·
shadow book (columns exist, nothing writes them — this is how formulas are supposed to earn their
weights) · bar pruning and archive · raw-filing archive · L0 market-cap floor applied to only ~572
of 2,783 names · API quota alarm in the brief · stage-level heartbeat status.

**Unjudged:** C2 memos and bench approval — `bench.approved` is false for all 67 rows, and
`daily.py` counts buyable only where `approved`, so **the compounder sleeve is hard-wired to zero
until R5 runs once** · CCN < 55 review memos · invalidator checks · entry snapshots · anniversary
re-underwrites · rejection cooldowns · formula version rows.

### 1C — Engineering debt that will cause the next bug

No tests, at all, for a system that sizes real money — four of the seven bugs found on 07-31 were
ten-line unit tests. No `requirements.txt`; `numpy`/`pandas` unpinned across nine inline YAML
declarations, and the worst backtest bug was a pandas `rolling()` default. `rank.py` and
`funnel.py` predate `db.py` and duplicate connection, heartbeat, retry and percentile code in a
different house style. No local dev path — every change costs a push, a dispatch and a wait.
`backup.py` and `migrate.py` carry no `DRY_RUN`. Tickets have no identity, which is why 45 rows
encode 15 decisions.

## Part 2 — Architecture decisions

Prototype, so these buy simplicity over generality. Each one is a call I am making; each is
reversible in a commit.

**A1 — Split the nightly job into two modules by *tempo*, not by topic.**
`src/duties.py` (nightly, after bars land) owns everything that must be true before the open:
M3 base re-scan and queue-state refresh, stops/trails, hurdle marks, event scan, blackout,
NAV, and **arming**. `src/rank.py` keeps only what §3.0 puts on Saturday: group RS, L1-M rebuild,
MCN, re-rank. This is the fix for the daily-trigger gap (§3.2's "re-scanned nightly") and it
removes the reason base detection was ever duplicated between `rank.py` and `backtest.py`.

**A2 — One `signals.py`, imported by the nightly job *and* both backtests.**
Base detection, M2, MCN sub-scores, breakout classification, pyramid schedule, stop ratchet and
hurdle math become pure functions over arrays, with no database and no I/O. Today the base
detector exists twice and the two copies already disagree with each other and with the plan.
A single implementation is also the only way a backtest can honestly claim to measure the live
system. **This is the highest-leverage refactor in the build and it comes before new features.**

**A3 — Tickets get identity and supersession.**
A ticket is keyed `(ticker, action, reason, round(trigger_price, 2))`. Arming upserts: an existing
`proposed`/`approved` row is refreshed, a row whose condition no longer holds is moved to
`cancelled` with a reason, and nothing is ever duplicated. First act of the migration: collapse
the 45 existing rows to the 15 real decisions. Without this, "45 proposed tickets" is what Zak
sees every morning forever.

**A4 — Jobs arm; sessions write. Enforced by a Postgres role, not by promise.**
§4.3's guard triggers already refuse non-owner writes to computed tables. Add role
`yuna_session`: read everything, write only `briefs`, `tickets`, `observations`, `transactions`,
`config`. Its URI goes in the Supabase MCP connector; `DATABASE_URL` stays owner and stays only in
Actions secrets. Then "Yuna never computes scores by hand" and "only sessions write tickets" are
both schema facts. Theme assignment (D11) lands naturally here — it is a session-written column.

**A5 — The five sessions are scheduled Claude Routines whose runbooks live in the repo.**
Each Routine's prompt is three lines: *you are Yuna, read `sessions/R1_preopen.md`, execute it.*
The runbook itself is version-controlled law reviewed like the formulas (§5 says exactly this).
R1 (13:00 UTC weekdays ≈ 6:00 PT), R2 (03:30 UTC ≈ 20:30 PT), R3 (15:00 UTC Sat) fire fresh
sessions with the Supabase and EODHD connectors attached, compose in the §5.0 voice, write to
`briefs`, and push to Zak's phone. R4 and R5 stay interactive — Zak opens them, because both need
his numbers and his rulings. A session that fails to write its `briefs` row did not happen, and
the missing push is the alarm (§4.7).

**A6 — Bulk ingest, with per-ticker demoted to the four exceptions §4.1 names.**
`eod-bulk-last-day/US` for the nightly tape, per-ticker only for cold start, corporate-action
refresh, gap repair, and names entering L0. Splits/dividends feeds arrive in the same commit,
because bulk adjusted closes are worthless without the re-pull that a split triggers.

**A7 — The backtest is a verification gate, not a research toy.**
It reads its parameters from `config` (so it cannot silently diverge), reports its grade
(§4.8), and gets re-run at the end of every phase that touches a formula. `backtest_trades.mcn`
is renamed `score` with a `sleeve` column, so a compounder row stops masquerading as momentum.

**A8 — Tests where a wrong number costs money.**
`pytest`, hand-built fixture arrays, no database, no network: base detection (incl. the two break
rules), M2, each MCN sub-score, breakout classification, pyramid, stop ratchet, hurdle solver,
C1, CCN renormalization, sizing, blackout in trading days, effective bets. Golden-value tests on
the plan's own worked examples — four names at 0.85 correlation → 1.1 bets; 8% stop at 0.7%
budget → ~8.8% position. CI runs them on every push. This is Tier 4 in the old audit and Tier 0
here, because every phase below is a formula change and I have no other way to know I did not
break the last one.

## Part 3 — The build, in order

Nine phases. Each has an exit gate that is a query or a test, not an opinion. Phases G–K are
mine; L is Zak's and mine together. Sizes are session-units of my work, not calendar days.

### Phase G — Foundations *(gate for everything else · ~1 session)*
`requirements.txt` with pins · `.env.example` and a `make`-style local runner · `pytest` + CI
workflow · `signals.py` extracted with tests, `rank.py`/`backtest.py` rewired to it (no behaviour
change intended, and the tests prove which changes were unintended) · `rank.py` and `funnel.py`
folded onto `db.py` · `DRY_RUN` in `backup.py`/`migrate.py` · shared `summarise()`.
**Gate:** CI green; `weekly-rank` output identical to today's row-for-row except where a test says
the old value was off-law.

### Phase H — Conform the formulas to the current plan *(~1–2 sessions)*
D1–D5, D8–D10, D13 from Part 1A. Each fix ships with the test that pins it and a one-line comment
citing the §. D9 gets the full data-confidence path (drop the component, renormalize, cap at band
bottom, flag for sign-off), not the growth-capping shortcut. D11's theme becomes a session-written
column on `tickets` and `book`, with sector kept as an *input* the memo shows.
**Gate:** for every row in Part 1A, a passing test named after it. Re-run both backtests — **this
is also the first honest measurement of the amended §3.2 confirmation rule (D6)**, and I expect
the momentum numbers to move materially, since 171 of 296 trades in the old run exited on a rule
that no longer exists.

### Phase I — The operating layer *(the missing half · ~2–3 sessions)*
`duties.py` per A1, with the arming engine per A3. Every row of §3.0's interrupt table becomes a
ticket: stop/trail fired → exit ticket same day · hurdle crossed → entry or add ticket · gate flip
→ sleeve-to-cash exits or re-arm · trend-template fail and MCN < 55 → exit tickets · blackout entry
→ cancel-order tickets, protective stops untouched · ±7% gap → check ticket. The pyramid state
machine advances `pyramid_step` on confirmed adds and freezes it at 50% while unconfirmed, with
the three-session late-confirm window and the close-below-pivot hair-trigger. The fill loop runs
`proposed → approved → provisional → confirmed`: a session writes the provisional `transactions`
row, the nightly job applies it to `book`, Sunday confirms it.
Then the §2 caps that are seeded and unread — 25% single name, +10 displacement with auto-drafted
swap tickets, 2 new entries per brief, 7–9 positions, sleeve ceilings — plus averaging-down tiers
and the crash protocol's tactical lots.
**Gate:** a dispatch run on a scratch snapshot produces the exact ticket set I can derive by hand
from §3.0 for that day, and re-running it produces zero new rows.

### Phase J — Safety and honesty *(~1–2 sessions)*
Quarantine with two-source agreement (job re-fetch + live quote) — no suspicious print may fire a
sell-side action. Corporate-action refresh + bulk ingest per A6. Delisted-name retention, which
un-flatters every backtest number in `docs/`. Shadow-book writes on every pass and exit with
30/60/90-day marks. L0 cap floor for all names, L2 composition per D12. Bar pruning to the 3-year
window with the archive commit. Quota alarm in the brief; stage-level heartbeat status.
**Gate:** an injected 45% phantom print is quarantined and produces no ticket; a synthetic 4:1
split triggers a history re-pull and no gap alarm; a nightly run costs a few hundred units, not
2,800.

### Phase K — The judgment layer *(~2 sessions)*
`sessions/R1…R5.md` runbooks, written from §5 verbatim, in the §5.0 voice. The three Routines per
A5, the `yuna_session` role per A4, and the delivery path proven end to end. R5 carries the C2
memo generator (top ~100 by CCN, template from §5.5) — **this is the switch that takes the
compounder sleeve off zero.** R4 carries the reconciliation flow: Zak's balances and credit in,
NAV trued, shadow marks recorded, discrepancies flagged and never absorbed. Plus the judgment
mechanics that hang off these sessions: CCN < 55 review memos within 48h, invalidator checks,
entry snapshots at purchase, anniversary re-underwrites, rejection cooldowns with recorded CCN,
formula version rows.
**Gate:** three consecutive weekdays where R1, R2 and R3 fire unattended, each writes its
`briefs` row, each reaches Zak's phone, and R1 on a stale-data day sends the banner with no new
tickets.

### Phase L — Cutover *(Zak's rulings, then mine · ~1 session + his time)*
Collapse the duplicate tickets. Zak rules on the six Phase 0 exits and the Step 5 levered verdict
(CNQ vs `VXC.TO`). Apply the verdicts: sleeves assigned, exits ticketed and filled, stops recorded
for every momentum position so §4.6 has state, entry snapshots written, themes assigned. First R5
approves an initial bench. Then the machine is in steady state by §6's own definition — and if
nothing is buyable that week, that is the system working.
**Gate:** `book.sleeve` has no `unassigned` rows · every momentum position has a stop and a
stop-limit · `select count(*) from tickets where state='proposed'` equals what R1 published this
morning · one full week runs with no manual intervention.

### Phase M — Steady state *(continuous)*
The weekly rhythm runs itself. My standing work becomes: read the amber, keep the shadow book
honest, bring formula-change proposals to R5 with shadow-book evidence rather than opinion, and
write the learnings-promotion spec once real observations exist (the plan defers it deliberately).

**Critical path: G → H → I → K → L.** J can slip one phase behind I without blocking cutover, but
not past it — going live without quarantine means a bad tick can sell a real position.

## Part 4 — What I need from Zak

**Blocking — the machine cannot finish Phase L without these**

1. **The six Phase 0 exit verdicts and Step 5.** Currently 0 keep / 6 exit / 1 to Step 5. Nothing
   moves until he rules, and the book sits sleeve-less and stop-less until he does.
2. **A first bench approval (R5).** `bench.approved` is false for all 67 rows and the buyable
   count reads `approved` — so no compounder can ever be bought until one R5 session runs.
3. **Every momentum position's actual broker stop.** §4.6's protection layer has no state. If
   Zak's GTCs exist, the machine does not know their prices; if they don't, seven positions are
   naked. This is the single most urgent item in this document.

**Plan edits I recommend — announced, exact-line, his call**

4. **§3.1 reinvestment floored at 0.** ANET, AVGO and VRT all compute `reinvest_rate = 0` because
   working capital released more cash than capex consumed, so the engine reads 0 for a company
   growing 27%/yr. The implementation is faithful; the formula systematically ranks
   negative-working-capital compounders — arguably the best businesses in the universe — at the
   bottom. Code cannot fix this without breaking the freeze.
5. **Momentum's structural under-deployment.** The backtest earned ≈27.6%/yr on capital deployed
   while averaging 12.7% of NAV in a sleeve permitted 40%. The edge is real and the machine will
   not deploy it. Phase H's re-run will re-measure this under the amended confirmation rule
   before we decide anything — but if the exposure gap survives, it is a §3.2 question (how bases
   are found and how many names may be armed at once), not a bug.
6. **Foreign issuers / ADRs.** §3.0 rules them into the compounder pipeline when FCF and market
   cap are in one currency, converting at fiscal-period-end FX. The code instead excludes all 224
   of them, TSM included — a stricter subset of the rule, and it is currently what disqualifies a
   position he holds. Either I build the conversion, or the plan ratifies the exclusion.
7. **The three announced deviations** in `score.py` — 3-year fair-multiple window instead of 5, the
   invented `pfcf_obs ≥ 8` threshold, the coarse census gate at $4/$5M — want ratifying or fixing.

## Part 5 — What "steady state" means, so we can tell when we are there

Ten statements, all checkable by query:

1. Five scheduled jobs run on cadence; every run writes a heartbeat row with stage-level status.
2. R1, R2, R3 fire unattended and reach Zak; R4 and R5 run on his weekend.
3. Every §3.0 interrupt produces a ticket the same session, and no ticket is ever duplicated.
4. Every momentum position carries a stop, a stop-limit, and a pyramid step the machine advances.
5. Fills close the loop to `confirmed` against the broker's settled record each Sunday.
6. NAV is anchored weekly and extrapolated daily, labelled provisional in between.
7. No sell-side action can fire off a single unverified print.
8. A split re-pulls history and raises no false alarm.
9. Every pass and every exit lands in the shadow book and gets marked at 30/60/90 days.
10. `stale data ⇒ no new tickets` is demonstrable: the switch has been tripped once, on purpose,
    and the brief still arrived.

Until #9 has a year of rows, every formula in this system remains version 1 of an experiment —
which is what the plan says it is. The build's job is not to be right. It is to be honest enough,
for long enough, that being right becomes measurable.
